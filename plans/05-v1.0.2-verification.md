# v1.0.2 verification: h700 rc11 pad and missing engines (2026-10-15)

## Issues

- #3: NextUI's H700 SDL (rc11 and later, `loveretro/h700-toolchain`
  `support/sdl2-h700.patch`) gives `ANBERNIC-keys` one fixed layout on every
  model under GUID `19000000010000000100000000016e01` and ships a positional
  default mapping for it (`a:b0`). The pak only mapped the old GUID, so that
  default won: A/B and X/Y swapped and, on stickless models, the d-pad drove
  `dp*` instead of the left stick, so the ScummVM pointer stopped moving.
  The patch's button table (B=0, A=1, Y=2, X=3, L1/R1=4/5, Select/Start/Menu
  =6/7/8, L3/R3=9/10, L2/R2 as axes 2/5, sticks 0/1 and 3/4) and NextUI's
  `platform.c` stick list (two sticks: rg40xxh, rgcubexx, rg34xxsp, rg35xxh,
  rg35xxpro; one: rg40xxv) match the issue's proposal and the launcher's
  existing model split.
- #2: the v1.0.1 release log shows configure dropping Hpl1 and Phoenix VR (no
  giflib) and QD Engine and Alcachofa (no libmpeg2). Both libraries are now
  built static from pinned tarballs. Hpl1 is then disabled on purpose (see
  below), so 101 engines become 104.

## Penumbra (Hpl1): left out

Tested with the Steam Windows release (`Penumbra.exe`
`384e33ddc55f51debca07b6538087e75`, detected as `hpl1:penumbraoverture`):

- Default renderer, RG SP and Brick: segfault about 4 s after launch. A crash
  handler preload put the fault in `hpl::cLowLevelGraphicsSDL::Init`, at its
  first GL call (`glGetIntegerv(GL_VIEWPORT)`), through an invalid function
  pointer. ScummVM offers Hpl1 the OpenGL renderers on GLES2 contexts, but
  this class needs desktop OpenGL (`glBegin`, 32-bit index draws).
- `renderer=software` (TinyGL), Brick: runs and exits cleanly, but the picture
  is striped/garbled on the panel, and after the intro text (about 55 fps,
  falling to 27) the 3D scene runs at 5-6 fps.

`--disable-engine=hpl1` keeps it out; the README lists Penumbra as
unsupported. Alcachofa prefers its shader renderer (GLES2-capable) and only
falls back to its desktop-GL path without shaders; Phoenix VR is 2D. Neither
was run, for lack of game data.

## Pilot Brothers 3 (QD Engine)

Russian Windows release (`qd_game.qml` `33dfc61046e5af85b570eda24e0afe6d`,
`bp4.exe` `fd5bcdcc1fc16c78aa51d67e550cc674`), detected as `qdengine:pilots3`.

- RG SP, launched from NextUI and played by hand (36 s of runtime in the
  log): no crash, normal exit. Presented frames: 46-60 fps, with one 9 s stretch at 16 fps.
  The log reports two missing sound effects (`клац.wav`, `клац2.wav`); neither
  name appears in the game's data, so this is a gap in the release, not in
  the pak.
- Brick, final build, started over SSH through the top-level `.m3u` (no
  input): reaches the main menu with a correct picture, 16-17 fps for the
  first 10 s, then 35-44 fps on the animated menu; the same two missing-sound
  warnings; exits on SIGTERM with nothing left behind.

NextUI opens a folder as a game only when it holds a same-named `.m3u` (or
`.cue`); a bare `.scummvm` makes it open the folder instead. The README now
shows the `.m3u` in the game layout.

## Observed warnings and limits

Brick logs the EGL config fallback and a 1881-versus-1024 mixer buffer
warning, as before. The first Smart Pro S launch after install logged three
`Could not queue pageflip: -16` lines from the firmware's KMSDRM SDL; four
further runs of the new build (two direct, two via the launcher) and three of
v1.0.0 logged none.

Brick, Smart Pro S and Miyoo Flip controls were checked over SSH, not by
pressing buttons; their launcher output is byte-identical to v1.0.1.

Killing `nextui.elf` to launch a game over adb powered the RG SP off (and cut
an adb copy short); launch from NextUI instead. Previous paks are kept as
`Emus/<platform>/.SCUMMVMSA-v1.0.x-backup` on each test device.
